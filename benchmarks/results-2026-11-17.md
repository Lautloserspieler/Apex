# Apex Benchmark Results – 2026-11-17

**Note:** These benchmarks reflect the state of Apex at the end of the phase that was implemented up to this point (minimal inference core + real GGUF support via llama.cpp backend). They serve as the baseline for subsequent optimization phases.

Hardware: NVIDIA GeForce RTX 5070 (12 GB), CUDA 13.4  
Models: Qwen2.5 Instruct (Q4_K_M)  
Context: 2048–4096, max tokens: 256, temperature: 0  
Binary: Apex CUDA build with llama.cpp backend

## Summary

| Model   | Device | Load (s) | TTFT (s) | Prefill (tok/s) | Decode (tok/s) |

| 3B      | GPU    | 0.469    | 0.062    | 1211            | 239            |
| 7B      | GPU    | 0.769    | 0.070    | 1082            | 123            |
| 3B      | CPU    | 0.882    | 0.834    | 89              | 24             |
| 7B      | CPU    | 1.885    | 1.907    | 39              | 11             |

## Notes

- GPU offloading worked fully for 3B (37/37 layers) and 7B (29/29 layers).
- Prefill performance on the RTX 5070 is strong.
- Decode throughput scales roughly as expected with model size.
- Flash Attention was reported as not supported and fell back (potential future optimization).
- TinyStories (656K) achieved ~9800 tok/s decode on GPU (expected for such a small model).

## Repeated official llama.cpp standalone benchmark — Fedora 44, 2026-11-17

A separate standalone `llama-bench` was built from the **same source archive pinned in Apex** (llama.cpp commit `ef3848f9d7d4cf7b6b2abfc3b4c960b55d6d9e91`, b12445) for both CPU and CUDA. The locally printed benchmark build string was `1dba144 (45)` (inherited Apex Git metadata); **this string is not the upstream llama.cpp source revision**. Model: official Qwen2.5-0.5B-Instruct Q4_K_M GGUF, previously recorded SHA256 `74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db`, size 462.96 MiB and 630.17M parameters, labeled `qwen2 1B Q4_K - Medium` internally by `llama-bench`.

### Standalone commands and measurements

```bash
MODEL=models/qwen2.5-0.5b-instruct-q4_k_m.gguf
build/llama-bench-cpu/bin/llama-bench -m "$MODEL" -p 37 -n 128 -t 4 -ngl 0 -dev none -b 512 -ub 512 -r 5
build/llama-bench-cuda/bin/llama-bench -m "$MODEL" -p 37 -n 128 -t 4 -ngl 99 -b 512 -ub 512 -r 5
```

| Standalone backend | Workload | Mean tok/s ± reported variation (5 repetitions) |
|---|---|---:|
| CPU, 4 threads, no accelerator | `pp37` | **372.10 ± 4.07** |
| CPU, 4 threads, no accelerator | `tg128` | **109.09 ± 0.18** |
| RTX 5070 CUDA, `ngl=99` | `pp37` | **11643.48 ± 3151.74** |
| RTX 5070 CUDA, `ngl=99` | `tg128` | **767.98 ± 1.12** |

The earlier, separate Apex Qwen ChatML benchmark ran one excluded independent warm-up process and five measured independent processes, with 37 actual prompt tokens, context 2048, output limit 256, greedy temperature 0. Its **medians** were:

| Apex backend | Measured decode tok/s (median) | Measured prefill tok/s (median) | Generated token count per run |
|---|---:|---:|---:|
| CPU-only build | 104.25 | 372.85 | 172 |
| CUDA build / GPU offload | 683.08 | 583.05 | 160 |

**Comparison limitations:** Apex values are medians from *independent model-loading processes* that stop on EOS, with live ChatML tokens and an explicit first-request prefill. Official `llama-bench` values are reported as means ± variation for separate *synthetic* `pp37` and `tg128` tests, likely with different cache/context and warm-up behavior; these figures are **not** aligned end-to-end timings, and no 'Apex overhead' or slowdown percentage is established. The GPU `pp37` variability (±3151.74 tok/s) is especially large, and its large difference from Apex's first-request prefill does not establish slower GPU kernels in Apex. The Apex GPU-versus-CPU decode ratio is also not an Apex-versus-llama.cpp speedup.

**Pending acceptance:** document matching end-to-end prompt/context/sampler/device/threads/warm-cache controls, collect raw standalone logs and per-run statistics, and compare with identical semantics before estimating integration overhead. The previously saved local Apex `report.json` and raw logs remain excluded from Git; the standalone table above is from the user-supplied terminal output. No timings have been independently rerun by CI.
